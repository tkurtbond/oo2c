Component: sanitizer
Version:   16.2.1 (Fedora 44, gcc version 16.2.1 20261029 (Red Hat 16.2.1-3)),
           x86_64-redhat-linux

Summary: -fsanitize=address use-after-scope: wrong shadow for a
variable moved into a nested function's FRAME at an offset that is
not 8-byte aligned (false "unknown-crash")

Testcase (t.c):

  struct pos { int a, b, c; };
  __attribute__((noinline)) void set(struct pos *p, int v) { p->a = p->b = p->c = v; }
  __attribute__((noinline)) void use(int *p) { *p += 1; }
  __attribute__((noinline)) int f(int n) {
    struct pos bp;                 /* in FRAME.f at offset 12 */
    int g(void) { set(&bp, n); return bp.a; }
    { int t = n; use(&t); n = t; } /* poison of t reaches l7 */
    goto l7;
  l7:                              /* re-unpoison of bp, misaligned */
    return g();
  }
  int main(int argc, char **argv) { (void)argv; return f(argc) != 2; }

  $ gcc -O1 -fsanitize=address t.c -o t && ./t

(Same result at -O0 and -O2.)  Actual:

  ==...==ERROR: AddressSanitizer: unknown-crash on address 0x7b9c07df004c ...
  READ of size 4 at 0x7b9c07df004c thread T0
      #0 ... in f
      #1 ... in main
  Address 0x7b9c07df004c is located in stack of thread T0 at offset 76 in frame
    This frame has 2 object(s):
      [48, 52) 't' (line 7)
      [64, 88) 'FRAME.1' (line 4) <== Memory access at offset 76 is inside this variable
  =>0x7b9c07df0000: f1 f1 f1 f1 f1 f1 f8 f2 00[04]00 f3 f3 f3 f3 f3

Expected: no error; the program is valid (exit status 0).
-fno-sanitize-address-use-after-scope avoids it, and so does
struct __attribute__((aligned(8))) pos (an 8-byte struct also works);
__attribute__((aligned(8))) on the variable bp does not.

Analysis:

bp is used by the nested function g, so the nested lowering moves it
into FRAME.1, at offset 12 (FRAME.1 occupies [64, 88), bp [76, 88)).
The use-after-scope marks are rewritten to the field
(-fdump-tree-nested):

      .ASAN_MARK (UNPOISON, &FRAME.1.bp, 12);
            .ASAN_MARK (UNPOISON, &t, 4);
            .ASAN_MARK (POISON, &t, 4);
      .ASAN_MARK (UNPOISON, &FRAME.1.bp, 12);   <- at label l7
      .ASAN_MARK (POISON, &FRAME.1.bp, 12);

The marks' expansion assumes the variable starts on an 8-byte shadow
granule, which is true for an ordinary stack variable in the ASan
frame but not for a field of FRAME.  The re-unpoison at the label
survives sanopt because the poison of t reaches it, and it leaves
shadow 04 for [72, 80), so bp.a at offset 76 is reported.

A second consequence: the epilogue resets only the shadow bytes that
the prologue set (the redzones), not those under variable bodies,
and FRAME's body is not reset either.  The wrong shadow byte therefore
survives f's return.  In the original program (code generated by the
Oberon-2 compiler oo2c, which uses nested functions and many labels)
there was no report in the function itself.  A later, deeper call
that used alloca/a VLA over the same stack (alloca poisons only its
own redzones) then got "unknown-crash" in memcpy into the VLA.

Possible fixes: give FRAME fields that get ASAN_MARKs shadow-granule
(ASAN_SHADOW_GRANULARITY) alignment, or not instrument them for
use-after-scope.
